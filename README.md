客户端把请求体编码成紧凑二进制再签名，同一份数据却签出了两种不同的摘要：头字节一律使用四字节长度字段，小值也输出非最短形式；解码器接受非最短长度形式，同一个数值因此对应两种合法字节串；映射键按字符串字典序比较而不是按编码字节序比较，整数键与文本键的次序错乱；映射出现重复键时后者静默覆盖前者而不报错；负数直接按有符号整数编码，与约定的取反减一映射不符；文本串未按 UTF-8 校验，非法序列被原样接受；不定长编码被接受并原样输出，规范化结果因此不唯一；浮点数用平台默认的双精度文本转换，精度与字节都不稳定；摘要对原始输入求值而不是对规范化字节求值；批量规范化复用上一份文档的排序结果，第二份文档沿用第一份文档的键序。cbor/canon.py 是核心，tests/test_canon.py 15个红。要修的是：按上面的顺序把 10 个缺陷逐个修掉。

题目定位
========

这是一道安全场景下的规范化实现题。客户端把请求体编码成紧凑二进制再签名，服务端必须对同一份语义数据得到唯一的字节序列与唯一的摘要。缺陷分布在最短编码、映射键序、不定长拒绝、标签与浮点表示四类问题上，逐个修补边界并不能收敛；需要先建立字节级契约，再按契约重写编码器与解码器。

规格契约
========

1. decode 只接受规范形式：非最短的长度与整数形式一律报错；不定长字节串、文本串、数组与映射一律报错；映射键重复时报错，包括解码后才发现相等的重复键；文本串必须是合法 UTF-8。
2. encode_head 必须按最短附加信息形式输出头字节，24、256、65536、4294967296 是长度形式的切换边界，任何值都不得使用固定四字节长度。
3. encode_int 非负整数用主类型 0；负整数用主类型 1，并按约定映射为负一减该值，因此负一编码为 0x20，负一千编码为 0x39 0x03 0xe7。
4. encode_bytes 区分主类型：bytes 用主类型 2，str 先按 UTF-8 校验再用主类型 3，非法文本不得被替换字符掩盖。
5. sort_map 按每个键编码后的字节序列做字典序比较，键的类型参与比较；整数键、字节串键、文本串键共处一个全序，输入顺序不得影响结果。
6. encode 生成规范字节：最短头字节、键按编码字节序排序、拒绝重复键、拒绝标签透传、拒绝不定长输出；浮点使用固定的大端双精度表示，不依赖平台、区域设置或浮点默认字符串化。
7. canonical_digest 先对值做规范编码，再对规范字节求小写 SHA-256 十六进制摘要；不得对原始输入、repr 结果或调用方提供的序列化直接求摘要。
8. canon_batch 对每份文档独立规范化，policy 取 canonical，其余取值报错；排序状态、缓存与键序在文档之间不得复用，结果中的 encoded 与 digests 与逐份调用完全一致。
